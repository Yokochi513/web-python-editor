# 0007. ビルドツールに esbuild を採用する

## ステータス

採用（2026-09-15）

## コンテキスト

[ADR 0002](0002-use-vanilla-js-html-css.md) で実装は素の JavaScript / HTML / CSS と決めたが、[ADR 0003](0003-use-codemirror6-as-editor.md) の CodeMirror 6 が複数の npm パッケージに分割された ES Modules として配布されるため、依存を結合するビルド工程は避けられない。

このビルドに求める要件は限定的である。

1. CodeMirror 6 の依存を解決し、1 ファイルに結合すること
2. Pyodide 一式（`pyodide.asm.wasm`、`python_stdlib.zip` 等）を静的アセットとして拡張パッケージへコピーすること。これらはバンドル対象ではなく、Worker からローカルパスで読み込む（[ADR 0004](0004-use-pyodide-as-python-runtime.md)）
3. 複数のエントリポイント（サイドパネル UI / Pyodide Worker / Service Worker）を扱えること

トランスパイルは不要である（ADR 0002）。検討した候補は次のとおり。

- **esbuild**: Go 製の高速バンドラ。上記要件とほぼ過不足なく一致し、導入する依存も実質ひとつ。ビルド定義は小さな JS スクリプトで書ける。アセットのコピーは npm script か短いプラグインで済む。
- **Vite**: `publicDir` によるアセットコピーは快適だが、**主眼である dev サーバと HMR が拡張機能では素直に機能しない**。HMR を得るには CRXJS 等のプラグインが別途必要で、それ自体が新たな依存になる。それを入れない場合、実質「設定の楽な rollup」であり esbuild に対する優位が小さい。
- **Rollup**: 実現可能だが、`node-resolve` やコピー用プラグインを個別に揃える必要があり手数が多い。ビルドも esbuild より遅い。
- **webpack**: 多機能だが、この規模には過剰で設定の重さが見合わない。
- **バンドラを使わず結合済みファイルを vendoring する**: 依存更新のたびに手作業が発生し、再現性がない。

## 決定

ビルドツールとして esbuild を採用する。

役割は**依存の解決・結合と静的アセットのコピーに限定**し、トランスパイルや構文変換は行わない。

## 影響

- `package.json` と npm による依存管理が入る。「素の JS で書く」方針（ADR 0002）は維持されるが、依存ゼロにはならない。
- 出力形式は ESM とする。MV3 は拡張ページの `<script type="module">`、モジュール Worker、`"type": "module"` の Service Worker をいずれも扱えるため、IIFE へ落とす必要はない。
- エントリポイントは サイドパネル UI / Pyodide Worker / Service Worker の 3 つを起点に構成する。
- **Pyodide のアセットは esbuild のバンドル対象から除外する。** wasm や zip をバンドルに取り込もうとしないよう明示的に扱い、コピー先のパスは Worker 側の読み込みパスと一致させる。
- ビルド成果物のディレクトリを拡張の読み込み対象とする。ソースツリーをそのまま「パッケージ化されていない拡張機能」として読み込むことはできなくなるため、開発時もビルドを挟む前提になる。
- HMR は使わない。変更の確認はビルド実行 + 拡張のリロードで行う。watch モードによるビルドの自動化までは esbuild で対応できる。
