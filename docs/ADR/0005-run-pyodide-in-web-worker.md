# 0005. Pyodide は Web Worker 上で実行する

## ステータス

採用（2026-09-15）

## コンテキスト

[ADR 0004](0004-use-pyodide-as-python-runtime.md) で Pyodide の採用を決めたが、それをどの実行コンテキストに置くかは未決定だった。Service Worker は待機状態が続くと停止されるため除外済みで、残る選択肢は次の 2 つ。

- **エディタ画面のメインスレッドで直接実行する**: 実装が単純。Pyodide と UI が同一コンテキストにあるため、出力の受け渡しも関数呼び出しで済む。ただし Pyodide はシングルスレッドで動作するため、**ユーザコードが実行されている間はメインスレッドが占有され、UI が停止する**。`while True:` を書かれた時点でエディタごと固まり、タブを閉じる以外の復帰手段がなくなる。
- **Web Worker に分離する**: UI スレッドが空くため、実行中もエディタは操作でき、`worker.terminate()` によって暴走したコードを強制停止できる。代償として、UI と実行基盤の間の通信が `postMessage` による非同期のメッセージ受け渡しになる。

本プロジェクトは任意のユーザコードを実行するエディタであり、無限ループや重い処理は事故ではなく通常起こりうる入力として扱う必要がある。停止手段を持たない設計は成立しない。

## 決定

Pyodide は Web Worker 上で初期化・実行する。エディタ画面は Worker と `postMessage` でやり取りし、UI スレッドでは Python コードを実行しない。

停止操作は `worker.terminate()` による Worker の破棄で実現する。

## 影響

- UI と実行基盤の境界がメッセージパッシングになる。実行要求・標準出力・標準エラー・実行完了・エラーをメッセージ種別として定義する。
- 標準出力は逐次 `postMessage` で UI へ送り、出力領域に追記する。実行完了を待ってまとめて送る方式は採らない（長時間実行中に何も表示されない状態を避けるため）。
- **停止するとランタイムの状態が失われる。** `terminate()` は Worker を破棄するため、停止後は Pyodide を初期化し直すことになり、初期化コストを再び支払う。停止後は Worker を事前に作り直しておき、次の実行を待たせない運用にする。
- Worker から DOM には触れない。描画は必ず UI スレッド側で行う。
- **`input()` による標準入力の実装は難しくなる。** Python 側は同期的に入力を待つが、Worker から UI へ問い合わせて応答を待つ処理は本来非同期である。同期的に待たせるには `SharedArrayBuffer` と `Atomics.wait` が必要で、そのためには cross-origin isolation が要る。拡張では manifest の `cross_origin_embedder_policy` / `cross_origin_opener_policy` の指定で有効化できる見込みだが、実装時に検証する。`input()` を当面サポートしないという判断もありうる。
- エディタ画面が閉じられると Worker も一緒に破棄され、ランタイムの状態は失われる。画面が閉じられやすい表示面（ポップアップ等）を選ぶと、初期化コストを繰り返し支払うことになる。表示面の決定（ADR 未作成）では、この点を判断材料に含める。
- Pyodide 一式は Worker から拡張パッケージ内のローカルパスとして読み込む。
