# 0025. `ready` を送る前に Python を一度暖機する

## ステータス

採用（2026-09-15）

## コンテキスト

[基本設計 §3.1](../design.md) は、Worker が Pyodide の初期化を終えた時点で `ready` を送り、UI が実行ボタンを有効化すると定めている。[ADR 0004](0004-use-pyodide-as-python-runtime.md) はエディタの表示と初期化を分離し、初期化の数秒をエディタの編集で埋められるようにした。

`loadPyodide` 自体の所要は実機で **1,423ms** だった（version 314.0.7、`spike/lifecycle-check/`、2026-09-15）。ここで測っているのは `loadPyodide` の完了までで、**その後の最初の `runPythonAsync` には追加のコストがかかる。** 実行の入口が初めて通るときに、`pyodide.ffi` や非同期実行の経路が読み込まれるためである。[pyodide-worker.md](../module_design/pyodide-worker.md) はこれを未決として残していた。

問題は所要時間の大小ではなく、**その時間がどこに現れるか**である。

- 暖機しなければ、コストは**実行ボタンを押した後**に現れる。押したのに何も起きない時間になる。
- 暖機すれば、コストは `ready` の前に隠れる。実行ボタンが有効になるのが遅れる。

`ready` が遅れている間、ユーザが待たされているとは限らない。エディタは初期化前から編集可能であり（[基本設計 §3.1](../design.md)）、パネルを開いた直後はコードを書いている。一方、実行ボタンを押した後の無反応は、**ユーザが結果を待っている時間**にそのまま乗る。

同じ長さの待ちなら、待っていない時間帯へ寄せる方がよい。これは実測を待たずに言える。

## 決定

`ready` を送る前に `await pyodide.runPythonAsync("pass")` を 1 回実行する。

`runPython`（同期版）ではなく `runPythonAsync` を通すのは、暖めたい経路が[基本設計 §3.2](../design.md) の実行と同じでなければ意味がないためである。JSPI のスタックスイッチングはこの入口を通った実行でのみ有効になる（[ADR 0012](0012-implement-stdin-as-terminal-with-jspi.md)）。

**暖機に失敗しても `initError` にはせず、そのまま `ready` を送る。** 暖機は最適化であって、実行の前提条件ではない。ここで失敗するなら本番の実行でも失敗し、そのときは通常の `error` として traceback つきで届く。暖機の失敗を初期化の失敗として扱うと、実行できたかもしれない状態を実行不能にしてしまう。

## 影響

- [基本設計 §3.1](../design.md) の手順 4-5 の間に暖機を入れる。「初期化完了時」に暖機までを含める。
- [pyodide-worker.md](../module_design/pyodide-worker.md) の `init` のフローに手順が 1 つ増える。標準入出力の差し替えを済ませた後に置く。**差し替え前に暖機すると、暖機の対象が本番と違う経路になる。**
- `ready` までの所要は `loadPyodide` の 1,423ms に暖機の分が加わる。[ADR 0004](0004-use-pyodide-as-python-runtime.md) の「初期化には数秒かかる」という前提は変わらない。
- 停止のたびの Worker の作り直し（[基本設計 §3.3](../design.md)）でも暖機が走る。停止直後に次の実行を待たせないという狙い（[ADR 0005](0005-run-pyodide-in-web-worker.md)）とは同じ向きである。
- 暖機の実測値は取っていない。**取らずに決めた。** 値が分かっても選択は変わらない——コストがあるなら隠す価値があり、無いなら暖機は無害である。
