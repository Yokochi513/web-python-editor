# 0004. Python 実行基盤に Pyodide を採用する

## ステータス

採用（2026-09-15）

## コンテキスト

エディタで書いた Python コードを実行する基盤を決める必要がある。Manifest V3（[ADR 0001](0001-implement-as-chrome-extension.md)）により、リモートコードの読み込みが禁止されるため、実行基盤は拡張パッケージに同梱できる方式に限られる。

検討した候補は次のとおり。

- **Pyodide**: CPython を WebAssembly にビルドしたもの。標準ライブラリをほぼ全面的に備え、言語仕様も本物の CPython。コアだけで概ね 10MB を超えるサイズが最大の難点。
- **MicroPython (WASM)**: 1MB 前後と非常に軽量だが、標準ライブラリが大幅なサブセットで、`json` や `re` 相当も完全ではない。
- **RustPython**: Rust 製処理系の WASM ビルド。未実装・非互換が残り、実行速度でも不利。Pyodide に対する明確な優位点がない。
- **Brython / Skulpt**: Python を JavaScript に変換して実行する方式。変換結果を `eval` / `new Function` で実行するため、**MV3 の拡張ページ CSP（`unsafe-eval` 不許可）に抵触し採用できない。**
- **ネイティブメッセージング / サーバ実行**: 互換性は完全だが、前者はユーザにネイティブホストの別途インストールを強い、後者は常時通信とインフラを必要とする。いずれも「ブラウザだけで完結させる」という本プロジェクトの前提から外れる。

判断の軸は互換性とサイズのトレードオフである。本プロジェクトでは **Python 標準ライブラリを必ずカバーすることを要件とし、そのためのサイズ増加は許容する**方針を採る。標準ライブラリが欠けた Python は、思いついたコードをすぐ試すという用途で体験を損なうためである。

## 決定

Python 実行基盤として Pyodide を採用する。

同梱範囲は **Pyodide コア + Python 標準ライブラリ** までとする。numpy / pandas 等のサードパーティパッケージは同梱しない。

## 影響

- 拡張パッケージのサイズは概ね 10MB を超える。これは受け入れる。インストールは一度きりで、以降のダウンロードは発生しないため、常用時の体験には影響しない。
- **`'wasm-unsafe-eval'` の CSP 宣言が必要**になる。manifest に以下を記述する。

  ```json
  "content_security_policy": {
    "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'"
  }
  ```

- Pyodide の既定の読み込み方法である CDN 経由、および `micropip` による PyPI からのホイール取得は、いずれもリモートコードにあたるため**使用できない**。ランタイム一式を拡張パッケージ内に配置し、ローカルから読み込む。
- **ユーザが任意のサードパーティライブラリを後から追加する機能は提供しない。** 将来対応する場合は、対象ホイールを同梱する形になり、サイズと引き換えの個別判断となる。この方針を変える場合は新しい ADR を起こす。
- Service Worker は待機状態が続くと停止されるため、Pyodide の実行場所として使わない。エディタ画面側に置く。具体的な配置（画面で直接実行するか、Web Worker に分離するか）は別 ADR で決定する。なお Pyodide はシングルスレッドで動作するため、ユーザコードの無限ループが実行コンテキストを占有する点が判断材料になる。
- 初回の Pyodide 初期化には時間がかかる。エディタ表示と初期化を分離し、初期化中もエディタは操作できるようにする。
- 標準入出力は Pyodide の stdout / stderr フックを介して UI の出力領域へ接続する。`input()` による標準入力の扱いは実装時に検討する。
