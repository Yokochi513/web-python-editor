# 0017. ADR に記録する決定は基本設計を変えるものに限る

## ステータス

採用（2026-09-15）

## コンテキスト

本プロジェクトは「設計過程の決定事項はすべて ADR に記録する。粒度は 1 決定 = 1 ファイル」という運用を採ってきた。決定の経緯を残すという意図そのものは変わらない。

モジュール設計書（[docs/module_design/](../module_design/)）を 5 本書いた結果、未決事項が 35 件挙がった。内訳は次の通り。

| 種類 | 件数 | 性質 |
| --- | --- | --- |
| 事実待ち | 6 | 決める余地がない。実機で確かめれば決まる |
| 根 | 3 | 他の未決事項を縛る |
| Figma 待ち | 4 | 設計判断ではなく画面設計の作業 |
| 葉 | 22 | 単独で決まる |

このうち大半は、キャレット位置を 1 点で持つか選択範囲で持つか、`setStdout` の `batched` の粒度をどうするか、といった**モジュール内部に閉じた選択**である。これらを [ADR 0012](0012-implement-stdin-as-terminal-with-jspi.md) や [ADR 0016](0016-replace-builtins-input-instead-of-setstdin.md) と同じ棚に並べると、ADR は現在の 16 本から 50 本規模になる。

**ADR の価値は決定が残ることではなく、後から引けることにある。** 一覧が 50 行になり、そのうち大半がモジュール内部の細部であれば、`input()` の同期化手段のような設計の骨格を成す決定が埋もれる。記録として残っていても引けなければ、残っていないのと大きな差はない。

一方で線を引かなければ、ADR にするかどうかが人によって、同じ人でも時期によってぶれる。判定の基準を決めておく必要がある。

## 決定

ADR に記録するのは、**[基本設計](../design.md)の記述を変える決定**に限る。それ以外の、モジュール内部に閉じた決定は、当該モジュールの設計書（[docs/module_design/](../module_design/)）へ直接記録する。

判定は次の一点で行う。

> **その決定を反映するために `docs/design.md` を書き換える必要があるか。**

必要があれば ADR を起こす。なければモジュール設計書に書く。

1 決定 = 1 ファイルの粒度は変えない。ADR となる決定については従来どおりとする。

## 影響

- README の「ADR の運用」に本基準を追記する。
- **モジュール設計書が決定の記録場所を兼ねる。** 未決事項として挙げた項目は、決定した時点でその欄から取り除き、本文へ決定として書き直す。未決のまま残った理由ではなく、決めた内容を残す。
- **判定に迷う決定は ADR 側に倒す。** 記録が過剰である方が、欠けているより後から直しやすい。モジュール設計書に書いた決定が後に他モジュールへ波及した場合は、その時点で ADR へ昇格させる。
- [ADR 0001](0001-implement-as-chrome-extension.md) から [ADR 0016](0016-replace-builtins-input-instead-of-setstdin.md) はいずれも基本設計に反映済みであり、本基準を遡って適用しても変わらない。
- 本 ADR 自体は基本設計を変えないが、**ADR の運用そのものを定める決定**であるため ADR として記録する。判定基準の適用対象外となる唯一の類型である。
